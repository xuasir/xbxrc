## Background / Goal

main 的 Browser 输入在短按、后台和发送积压下存在漏采、8 状态溢出丢边沿、模拟扳机峰值合并消失、普通释放延迟及 50ms 恢复轮询等待。目标为提高可观察的高频输入完整性、收紧输入年龄、加快释放和缓冲恢复。

## Scope

沿现有 BrowserGamepadBackend、公共 InputController、GamepadDriver、InputService 和 input DataChannel 修复。公共归属、游戏映射、Tauri/Rust 职责及有序可靠 SCTP 合同保持现有主线。实机启动、远端串流和长测由用户手动验收。

## Plan

1. 单一 Browser 后端协调 rAF 与 4ms 定时补采；相同状态按 100ms 心跳发布，变化当次发布，避免把高频补采放大为 UI 重算。
2. GamepadFrame 增加可选观测时间、采样身份和交接原因，兼容既有自定义 Driver；交接即使中性态相同也提交释放。
3. 有界队列预算改为 128 状态 / 250ms；数字边沿和扳机值变化保留，连续纯摇杆状态采用最新值。超时或硬容量耗尽执行显式中性重置及当前状态同步，并记录损失原因和数量。
4. 普通松开、扳机回落、摇杆归零和设备交接享有释放余量；前置按下保持顺序，优先暂停 metadata，报文大小计入水位检查。
5. DataChannelHub 提供有生命周期清理的 bufferedamountlow 订阅，InputService 恢复时直接 flush；50ms 定时器保留为拒发重试兜底。
6. 记录输入观测年龄、队列等待、积压量和完整扳机/摇杆状态；模拟值的逐包 trace 降频，数字边沿与降级保留证据。

## Risks

- Gamepad API 提供系统/浏览器的当前快照；事件循环冻结或平台状态更新受限时，物理边沿可辨识性由实机证据确认。
- 任意长拥塞与有界低延迟队列存在容量/年龄边界；超过 250ms 时明确放弃旧动作并重建当前状态，避免恢复后批量触发旧动作。
- 有序可靠通道中已接受的报文持续遵循原有顺序；本地释放余量加快入队，实际远端时延仍受网络重传和游戏处理影响。
