## 背景与目标

现行接收统计缺少 jitter-buffer 与 decode 的累计耗时及窗口均值；监督 tick 的时间取值跨越异步依赖。Metal YUV 转换固定使用 BT.601。音频配置继续满足 M137 VoiceProcessingIO 的有效输入合同，同时需要消费 Opus 协商声道并校准实际输出。

目标是在现有 Rust 会话/监督、libwebrtc 接收/解码和 Metal presenter 中修正三项路径，使接收缓冲、解码和音频输出均可从 trace 复盘，SDR 色彩按实际帧元数据处理。

## 范围与实施

1. 扩展 RTC stats 的累计缓冲/解码耗时、计数与窗口均值；按 inbound stream 隔离基线，计数重置和缺失值保留未知。全部异步依赖完成后捕获监督判定时间及事实快照，将可观测缓冲事实接入已有公共观察窗口。
2. 读取 CVPixelBuffer 的 YCbCr matrix、primaries 和 transfer 附件，选择 BT.601 / BT.709 / BT.2020 SDR 矩阵及全/有限范围偏移；按配置变化缓存矩阵与输出 colorspace。缺少元数据时使用明确的 SD/HD 回退规则，保持原有零拷贝、I420 兼容和 MetalFX 接线。
3. 音频生命周期观测 Opus 协商及系统路由；本地 PCM、首选采样率和 I/O buffer 消费固定 M137 默认 ADM 的单声道 / 48kHz / 20ms 合同，保留 playAndRecord/voiceChat。记录远端、PCM及设备输出声道、实际采样率、路由和延迟，健康路由事件由 SDK 处理设备格式，协调器更新观测。

长时稳定性、温控、GPU 动态预算由用户指定留到后续。网络恢复策略、技术栈与上屏健康归属继续沿既有合同。
