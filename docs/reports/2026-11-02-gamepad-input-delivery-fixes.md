# 手柄高频采样与输入交付修复报告

## 完成结果

- 日期：2026-11-02
- 分支：main
- 依据：[输入整链审计](2026-11-02-gamepad-input-chain-audit.md)、[修复 RFC](../rfcs/2026-11-02-gamepad-input-delivery-fixes.md)
- 状态：代码修复、自动回归与构建完成；实机串流/Windows掌机/长测继续按平台验收执行。

本轮修复短按补采、8 状态积压丢边沿、模拟扳机峰值合并丢失、普通释放阻挡、归属交接的中性态去重以及缓冲恢复等待。当前实现继续使用公共 InputController、既有游戏映射和有序可靠 input DataChannel。

## 交付行为

| 问题 | 修复后的行为 |
| --- | --- |
| rAF 间隔和暂停期间漏采 | Browser 后端的 rAF 和 4ms 定时器共用一个采样函数；变化立即发布，相同状态每 100ms 发布心跳 |
| 9 个交替状态积压后折叠 | 状态队列扩为 128 项，普通短时拥塞完整保留数字边沿 |
| RT 轻压→深按→轻压的峰值丢失 | 模拟扳机有效值变化单独保留，纯摇杆连续更新采用最新值，摇杆归零单独保留 |
| 普通松开/断开等待普通水位排空 | 部分数字按键松开、扳机回落、摇杆归零和设备交接使用 1KiB 释放余量；前置按下保持顺序，metadata 为输入让出空间 |
| 同为中性态的菜单/设备交接被 Driver 去重 | owner、设备和控制配置交接具有显式原因，取消旧源积压并建立中性基线 |
| 缓冲恢复额外等待 50ms | bufferedamountlow 在缓冲降至 8KiB 时直接触发 flush；50ms 轮询保留拒发兜底 |
| 拥塞恢复批量重放陈旧动作 | 旧输入超过 250ms 时清空旧队列，发送中性态，再同步新鲜最新状态；最新状态也过期时保持中性态 |
| 高频发送扩大逐包 IPC | 常规模拟状态及拒发事件按 100ms 节奏记录；数字边沿和重置保持独立记录，扳机峰值纳入采样窗口 |

报文实际字节数参与 16KiB 普通水位及 17KiB 释放水位检查。成功发送后才提交协议序号、metadata 和输入出队。订阅在停止/通道关闭/会话替换时释放，代际校验隔离已经捕获的旧回调。

## 模块与诊断

- `browser-backend.ts`：高频补采与重复快照抑制。
- `GamepadDriver.ts` / `domain/input.ts`：可选逻辑观测时间、物理采样时间、采样序号、owner/device/controls 交接原因；既有自定义 Driver 保持兼容。
- `InputService.ts`：边沿/扳机保持、纯摇杆合并、释放余量、128 项 / 250ms 预算、buffer 恢复订阅与限频诊断。
- `DataChannelHub.ts` / `BaseChannel.ts` / `InputChannel.ts`：带生命周期的 bufferedamountlow 接线。

`gamepadFrameSent` 增加 `sampleSequence/sampledAtMs/observedAtMs/observationToSendMs/queueWaitMs/pendingInputs/bufferedBytes/reset`，并记录全部按键、左右摇杆及扳机当前值/窗口峰值。`gamepadInputBackpressure` 记录降级原因、重建前清空的条目数、等待年龄和重建后保留条目数。

## 运行边界与手动验收

4ms 是调度目标。Gamepad API 的底层状态更新、系统限流和 WebView 主线程停顿决定实际采样精度；完整落在平台两次状态更新之间的物理动作继续需要实机核验。有序可靠通道中已接受的报文保持原有发送顺序，远端收到及游戏处理的即时性由网络和服务器共同决定。

128 项 / 250ms 是明确的容量和时延预算。超过预算时会放弃陈旧动作并重建当前状态，trace 可复盘；长期断网的动作完整性与低延迟有实际边界。

建议手动验证连续射击、RT 轻压快速拉动、摇杆+扳机+多键并发、菜单/系统覆盖层往返、持键断开及弱网恢复，重点观察远端持键持续时间、输入到画面响应的 P95/P99 和长测。此次自动验证覆盖代码及模拟链路，实机验收继续归入现有 Browser stable P0 / 平台待验范围。
