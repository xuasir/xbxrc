# 浏览器策略重设计：源画质保真、按故障域控制、稳定新帧供给

## Problem Framing

用户本轮明确的优先级是策略正确性和运行效果：稳定网络维持画面与帧节奏，高 RTT 云游戏获得符合路径延迟的稳定处理，1440p 源开启 SR 后保持至少源分辨率的信息量，采集与告警服务游玩主链。

推荐整体替换当前跨域画像和自动显示降档的决策方式。用户目标、实际源、显示几何与设备能力决定基础显示计划；传输、解码、renderer 各自在其证据范围内处理故障；观测提供解释与有界计数。正常运行维持当前有效计划，持续故障才进入有界动作和效果验证。

当前已按此方向完成 S0–S3 及新日志后的标准 SR 输出、帧计数补足与立即提交修正。全量 44 文件 / 326 项测试、18 项报告 fixtures、lint、类型检查与生产构建通过。交付证据见[代码改造验证记录](../../dev-docs/validation/2026-10-29-browser-policy-code-validation.md)与[本轮专项验证](../../dev-docs/validation/2026-10-29-browser-standard-output-and-latest-frame-validation.md)；[Mac/cloud 日志](../../dev-docs/validation/2026-10-29-browser-policy-fresh-trace-validation.md)作为修复前基线保存，新构建运行效果与 S4 完整配对/长测继续验收。

16:47 新构建[持续前台查验](../../dev-docs/validation/2026-10-29-browser-standard-output-fresh-trace-validation.md)与本批源码指纹匹配。标准输出、源下限及退出资源闭环通过；接收/解码/video稳定约30fps，marker与SR提交记录约3.6fps。用户补充实际观感明显好于3fps，后续先核验video/canvas可见层与绘制记账，再定位共享帧源；1440p成本、采样边界与共享样本继续验收。

## Current Constraints

- 保持 Tauri + Vue 3 + TypeScript + Rust 和现有浏览器 WebRTC/runtime 装配，复用当前协商队列、PlaybackService、renderer plan、共享帧源和连接 coordinator。
- 保留主机/云游戏、输入、音视频、显示设置、SR、截图、麦克风、统计导出和故障回退。自动适应的成功能力保留，其触发规则、权限和默认行为以本轮体验合同校准。
- 浏览器内部 TWCC/GCC、NACK/PLI/FIR、jitter buffer、解码与 compositor 的能力由平台拥有；应用层使用现有 API 和已验证能力。Rust 主线的传输与恢复职责保持原归属。
- 新方案承接[完整功能优化 RFC](../rfcs/2026-10-28-browser-runtime-simplification-and-stability.md)、[策略正确性审计](../../dev-docs/validation/2026-10-29-browser-render-policy-correctness-audit.md)。本轮用户要求更新了[10 月 23 日 SR 设计](../rfcs/2026-10-23-super-resolution-tier-redesign.md)的源下限与显示预算合同。

### 整改前已确认的策略连锁

| 代码事实 | 影响机制 | 本轮处理决定 |
| --- | --- | --- |
| `browser-runtime-profile.ts::evaluateProfileBandwidthState` 用 `presentAgeMs`、实际码率/请求上限、feedback interval 等任一阈值判 warning/congested | 本地呈现停顿和低运动编码量也能改变带宽画像 | 网络事实按字段来源、时间覆盖和本域原因解释；呈现年龄归显示域，码率占请求比归诊断 |
| `browser-runtime.ts::classifyRecoveryCause` 中 `lowBitrate` 单项可判 networkCongestion，也可为高 RTT 提供佐证 | 较高的用户码率上限让同一静态画面更容易进入网络恢复解释 | 删除该比值的拥塞决策权，健康静态画面保持有效计划 |
| `highRtt` overlay 把 mild packet/present age 收紧到 200ms，feedback interval 收紧到 280ms | 长路径更容易跨固定告警边界，呈现异常继续进入带宽分类 | RTT 归路径基线和恢复等待时序；本地提交按本地帧时钟判断 |
| `resolveAdaptiveRenderProfile` 和动态 RCAS 消费 bandwidthState、qualityLadderLevel、码率占比 | 网络标签直接改变锐化、shader preset、处理模式；displayL1/L2 还改 fit | 删除网络到渲染参数的控制边；fit、色彩、锐化由用户意图决定 |
| callback gap 直接成为 renderBackpressure，连续三个观察进入 displayL2 | 源供给稀疏、callback 合批和本地绘制压力共享同一个降档入口 | 各段帧事实分别判断，renderer 压力需要当前 renderer 的实际提交与成本证据 |
| L2 的 1080p/DPR1 输出上限进入 SR 的显示需求 D，之后再做两级 clamp | 1440p 先压到 1080p/960p，再铺满窗口；plan 标签与 backing 尺寸也可能错位 | 源尺寸下限覆盖每级计划/分配/执行检查；真实显示几何与成本预算各有语义 |
| 250ms 接收 FPS 写进 `stats.fps`，内容分类将它当显式源 FPS；SR 固定间隔并重置 lastFrameTime | 收帧波动改变 30/60 预算；144Hz/60 目标生产函数理想上界为 48fps | 接收吞吐、源节拍、用户帧率上限分开；新帧驱动，必要限流使用累计截止时间 |
| video RVFC 推进被当作 presentFps；SR drawCount 只进入资源诊断 | video 健康推进时 canvas 少绘的差值缺乏直接监督 | 当前 renderer 提交进展接入显示事实，帧链逐段展示 |
| callback 异常逐次 RPC，Rust recorder 才做 profile 过滤；GPU 查询进入每帧路径 | 观测和重复配置增加主线程/驱动负担，具体占比尚待分项测量 | 热路径有界计数，前端先过滤，已有采样节拍汇总，资源检查绑定资源变更 |

日志中的 55 次显示事件、25 次 FPS 预算变化、33 次 SR 冻结支持实际计划反复变化。72.152s 前台同代际窗口接收 29.92fps、解码 28.37fps、SR 提交 14.21 次/s，损失同时存在于解码、回调交付和 SR 提交。掌机具体损失分布继续以其设备日志核验。

这批 Mac cloud 日志还包含真实丢包和 jitter-buffer 积累，传输侧需要独立处理。home 两次会话在注册阶段超时，媒体 runtime 尚未启动；稳定 LAN 的策略行为通过合同用例和后续主机媒体样本分别验证。

## Options

| 方向 | 收益 | 代价与适用性 |
| --- | --- | --- |
| A：继续放宽现有阈值与驻留 | 改动较小，减缓触发频率 | 跨域输入、码率比值和源下限例外持续存在；后续校准仍依赖多套互相影响的档位 |
| B：用户保真基线 + 按故障域动作 + 效果验证 | 明确控制权限，健康路径零画质动作，删除跨域分支并保留故障恢复 | 需要同步修订输入类型、帧事实、监督消费与边界测试；采用此方案 |
| C：全部采用原生 video | 确立原生性能/画质对照基线 | SR、USM/CAS 与现有增强功能的用户需求仍需当前渲染路径；适合作为对照与保真回退 |

## Recommended Direction

### 1. 基础显示计划保持确定性

基础计划只接受用户显示意图、当前有效源尺寸、真实视口/像素比例、能力和当前 renderer 故障状态。网络 RTT/loss/码率、告警标签和 250ms 吞吐样本退出显示计划输入。

同一组有效输入得到同一输出；周期监督、网络画像变化与告警刷新保持计划恒定。当前已有 plan/attach/update 链继续作为唯一执行链。用户目标、当前有效计划、实际执行结果各自保存必要事实，兼容 UI 标签从这些事实派生。

现有 `homeLan/homeRelay/cloud` 标签保留为诊断及连接阶段上下文；多个故障域各有实际状态。移除用单一 dynamic 主标签覆盖网络、解码、显示的混合阈值表，以及由该表驱动的显示 ladder。旧档位字段的兼容投影在消费者迁移后清理。

### 2. 源画质下限覆盖所有执行分支

设 `S` 为当前真实源尺寸，`V` 为保持用户 fit 后的物理显示需求，`T` 为用户 SR 目标。尺寸比较沿相同画幅等比进行，宽、高均保持源下限：

```text
srOutputWidth  >= sourceWidth
srOutputHeight >= sourceHeight
```

| 场景 | 输出/算法合同 |
| --- | --- |
| 1440p 源、1440p 显示 | 至少 2560×1440 的处理 backing；等尺寸呈现跳过 EASU，锐化按用户意图与稳定基线处理 |
| 1080p/720p 源、1440p 目标 | 按当前用户 SR 目标和真实显示需求重建；正常计划补到目标，源下限持续成立 |
| 源高于显示需求 | SR 内部保留源尺寸，最终视口由显示合成阶段映射；原生 video 也可承担该映射 |
| 用户请求 1080p、实际收到 1440p | 以 1440p 实际源为下限；请求值用于协商目标与诊断 |
| 原生尺寸超过 GPU 纹理/分配能力，或 SR 持续成本过高 | 转入现有保真呈现回退，优先选择足够承载源尺寸的现有路径；记录实际路径和原因 |

真实 viewport/DPR 只回答显示几何，GPU 成本只回答当前增强是否能承担。成本预算触发增强回退；源像素下限持续覆盖 ladder、plan clamp、renderer clamp、texture/FBO 分配和截图。小视口、系统缩放、高刷新率、网络与观测状态都遵循同一源下限。

输出像素保留和感知质量分别验收。增强算法的软化、振铃、色彩偏差通过同源截图与 SR 开/关对照测量；等尺寸优先保真，用户锐化配置保持生效，压力回退保留原生源。服务实际下发 720p 后，新的源事实如实记录为 720p，SR 重建尺寸与远端源清晰度各自报告。

### 3. 各故障域只执行有因果依据的动作

| 域 | 权威证据与状态 | 允许动作与效果 |
| --- | --- | --- |
| 网络/传输 | 当前路径、可用 loss/repair 事实、RTT 相对路径基线的变化、网络 jitter、持续供给/缓冲趋势；缺失为 unknown | 浏览器标准拥塞控制与恢复继续运行；持续拥塞且能力已验证时，通过现有队列请求一次有限码率适应，核验远端反馈与供给效果 |
| 解码 | 同窗 received/decoded 增量、有效 decode 成本、freeze 和源供给 | 已确认持续解码故障时，执行既有关键帧/播放局部恢复；重复压力需新的本域证据和效果。编码能力适配作为显式用户/能力选择管理 |
| 帧交付/主线程 | callback 数、video advancement、mediaTime 有效性、callback lateness、调度延迟 | 合批与稀疏作为交付事实；按当前可交付 latest frame 调度，确认阻塞时收敛主线程工作 |
| renderer/显示 | 当前 generation 的新帧输入、真实提交次数/年龄、CPU 提交成本、可用 GPU 成本、尺寸与硬错误 | latest-only、修正节拍、资源复用；确认增强成本持续超预算后执行一次保真回退，并配对验证成本/供帧 |
| 生命周期/控制 | visible/hidden、Failed/Closed、当前连接/通道实际进展 | 复用公共生命周期与有限连接预算，隐藏段隔离、可见后取新鲜事实，硬断链按现有协调器处理 |
| 观测/告警 | 同样本事实、freshness、缺失原因、预算与聚合计数 | 更新面板、导出、去重告警与耗时摘要；观测故障由观测链处理 |

`actual bitrate / requested cap` 表达编码结果与用户上限的关系。静态场景本来可以用较低码率，拥塞判断要求真实传输证据。packet age 表达媒体入包新鲜度，源间歇、线程调度和真正断供分别结合其他事实解释。TWCC feedback cadence 只有在平台确实提供该字段和对应来源时才参与解释。

接收活跃、解码推进、renderer 停滞时，故障所有者归 renderer；解码不足时，本地 SR 输出下限仍保持。必要的能力或编码目标调整沿现有配置/协商入口表达，当前自动网络策略保持其传输权限。

### 4. 高 RTT 的维稳方式

按当前 candidate pair 建立带来源和新鲜度的路径 RTT 基线，基线在足够覆盖的健康窗口更新，路径切换重置。高绝对 RTT 表示基础路径延迟；持续增量、loss/repair、jitter 与供给积累共同说明额外压力。

稳定高 RTT 时维持用户画质、帧率上限、SR 尺寸和锐化。恢复等待与动作效果观察覆盖实际路径响应时间，采用有上限的时间窗和现有 episode 期限。应用显示提交的截止时间依据本地帧时钟与可用显示机会，远端 RTT 留在传输域。

持续拥塞时优先由标准 WebRTC 控制修复供给；有明确远端能力时做一次受限请求，保留用户目标并观察真实效果。现有 `requested/negotiated/observed` 三项分列；服务忽略请求记为 unsupported/无效果，暂停该 episode 的重复同请求。接收端自己渲染更多像素对网络往返延迟的因果作用为零，显示计划持续独立。

低延迟目标继续执行：跟踪 jitter-buffer 的实际积累和供给长尾，解码后的过期帧使用 latest-only 有界交付。现有浏览器控制与 API 能力范围决定可执行手段；媒体故障达到有限恢复期限后给出准确失败反馈。

### 5. 新帧驱动的绘制节拍

正常调度由共享帧源发出当前 generation 的新 marker，在可用显示机会处理最新帧，同一新帧至多一次实时增强处理。30fps 源自然供给约 30 次绘制，60fps 源在 90/144/165Hz 屏拥有接近 60 次新帧绘制机会。

共享帧源内的 rAF 可用帧计数补足稀疏 RVFC，原始 metadata 与补足帧按统一增量去重；SR 收到新帧立即尝试提交。接收帧率请求保持用户目标，隐藏预算只暂停本地绘制；网络适应保持既有有限码率权限。SR 放大输出采用 1080p/1440p/2160p 标准尺寸，真实视口用于选档和最终映射。

额外限流只消费明确用户/协商帧率上限和显示槽位，必要时用累计截止时间维护平均节拍，延迟过大直接取最新候选。250ms 实际接收吞吐、缺证的源 FPS 分类和 callback 抖动保留为观测。源 FPS 未知时保持用户目标和新帧驱动。

每个代际最多一份 latest 候选和一次待调度机会；等待新帧时按需唤起，隐藏时暂停绘制，截图请求用现有可取消有界队列单独处理。用户设置热更新和真实源尺寸变化继续生效。

### 6. 软异常经过时间覆盖、单动作与效果闭环

复用当前 3s/15s 有界采样窗口：短窗确认持续症状，长窗确认背景与恢复。以真实 elapsedMs、字段可用性和样本身份计算覆盖；同样本重复读取与到达乱序保持幂等。

初始软动作规则：当前域具有完整短窗症状覆盖和本域佐证后，执行一个动作；同域下一次软动作间隔至少一个 15s 长窗，并先完成上次效果观察。网络效果观察至少覆盖短窗与两次有效路径 RTT，且服从公共 episode 的有界期限。恢复增强先取得完整健康长窗，再进行一次有界试探；失败回到已验证路径，下一次尝试需要新的用户意图或新能力/源上下文。具体成本门槛由目标设备数据校准。

启动期等待足够事实，基础画质从用户目标开始；warmup 管理观测资格和恢复时序。硬 context/shader/FBO 失败与 Failed/Closed 事件及时进入现有故障动作；软窗口与硬故障事件各有入口。所有规则共用既有采样节拍和有限 episode。

这些时间值是首轮验证起点。代码策略的重点是输入权限、连续时间覆盖和效果闭环；新增阈值先按最小集合实现并用边界/设备数据校准。

### 7. 帧链、告警与观测开销

面板和报告至少分列 received、decoded、video/compositor advancement、callback delivery、当前 renderer submitted；CPU draw 提交和实际 scanout 各有语义。当前 renderer 的提交年龄监督 canvas，video 路径依据其自身可观测事实监督。GPU 时间和真实上屏字段缺失时展示 unavailable。

每段计数按相同有效窗口和 generation 对齐。received→decoded 的缺口进入解码/浏览器内部供给审查；decoded→callback 结合 video advancement/lateness 区分合批和交付不足；callback→draw 区分主动上限、latest 覆盖、调度错过、提交失败和截图额外绘制。上游帧身份缺失时用吞吐差和边界误差表达证据强度。

告警显示故障所有者、持续时间和已验证效果。高 RTT 可作为路径信息；持续拥塞、显示供给故障和观测缺证各自呈现，文案与颜色刷新独立于媒体动作。同域 episode 告警去重并跟随实际恢复关闭。

采集保留当前 250ms single-flight，帧热路径只做有界数字累加；按已有 1s 发布节拍汇总 callback、drop、backpressure 和耗时分布。真实故障/边界即时记录；前端入口按启用/profile 判定后再构造 payload/发 IPC，序列化和上传有界，导出保留关键故障链。

FBO 完整性检查绑定创建/resize，uniform/texture/FBO 按真实配置变化复用；运行期错误检查采用有界策略，context loss 等硬错误保持及时回退。CPU 提交耗时、GPU 异步耗时、getStats/解析/聚合/策略/trace 各自采样，避免把异步 GPU 工作归为同步 draw 成本。观测开关/面板开关配对比较新帧供给和 CPU/长尾。

## Open Questions

已确定的体验合同是源画质下限、控制域隔离、正常计划稳定和单动作效果验证。以下缺证事项作为实现验收项推进：

1. 掌机的实际源/viewport/DPR/刷新率、WebView/GPU 能力、SR 开关配对画面与成本，需由用户设备日志绑定。
2. 浏览器 RVFC 稀疏与主线程/GPU/合成器节流的具体占比，当前日志支持帧差，分项计时和真实 scanout 继续补证。
