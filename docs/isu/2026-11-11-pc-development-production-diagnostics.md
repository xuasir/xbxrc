# PC 开发与生产双模式诊断方案

日期：2026-11-11。状态：方案已确认，首版源码与自动验证完成。当前依据为 `main` 的 Browser 桌面线路，主窗口直接梳理。

首版以用户最后补充的“常规 / 轻量、异常与手动时间窗口历史可回溯”为准：默认常规 5 秒写盘，轻量 30 秒；最近 10 秒安全摘要缓冲；历史最多 12 条 / 64 MiB。实际范围与验证见[首版 RFC](../rfcs/2026-11-11-pc-diagnostics-first-version.md)及[实施报告](../reports/2026-11-11-pc-diagnostics-first-version.md)。下文的扩展能力与预算比较保留方案探索依据。

## 问题定义

PC 初步稳定版需要同时满足两个目标：开发期间快速看清运行过程；发行后在偶发故障或主动复现时获得足够证据。产品概念收敛为开发模式和生产模式，日志、调试工具、诊断面板共同遵循一个有效模式。

推荐由构建环境确定有效模式。开发模式自动提供详细观测与开发工具；生产模式默认常规后台采集，稳定运行时可切轻量，请求失败可直接导出对应问题，用户可主动采集复现过程。

2026-11-11 交互修订：生产端围绕“失败直接导出、主动采集、后台自动记录问题”组织。高级诊断展示当前状态、开始采集、导出日志、常规 / 轻量选项和历史记录；导出直接调用系统保存对话框。稳定时采用有界上下文缓冲与低频写盘，异常时自动保留详情，恢复后回到用户选择的后台档位。主动采集可随页面收起或应用最小化继续运行。

诊断包支持时间线回放、故障定位和复现条件重建。真实问题复现依赖对应构建、配置、操作、平台与网络条件；外部 Xbox 服务、远端视频内容和驱动状态通过测试环境或夹具重新验证。

## 当前约束与实现依据

### 已有能力

| 当前实现 | 本方案的衔接 |
| --- | --- |
| `runtime_trace_mode` 提供 `off / production / dev`；debug 默认 dev，release 默认 production | 收敛为两种有效模式，设置页展示实际生效结果 |
| Rust release 将存储的 dev 归一化为 production；前端还通过 `import.meta.env.DEV` 判断能力 | Rust 提供统一的有效策略和构建能力，前后端启动时核验一致性 |
| 设置页同时展示“运行时追踪日志”和“调试模式” | 高级诊断改为当前模式、采集状态和问题取证操作 |
| `debug` 当前参与配置定义、归一化、分组和展示；本轮检索覆盖的生产路径中，其职责集中在配置层 | 清理旧字段，开发工具具有明确的能力与调用入口 |
| 生产串流具备 1Hz 整窗健康摘要、30s 检查点、结束摘要、输入结果配对 | 作为常规记录合同；轻量策略保留聚合证据与有界上下文 |
| 生产异常窗口为前 5s / 后 10s、约 4Hz，具有冷却与字节预算 | 自动故障与用户标记复用同一异常窗口机制 |
| Rust writer、真实入队回执、有限期限 flush、有序轮转均已落地 | 继续承担记录、持久化、丢失计数和导出截止点 |
| 导出当前为本次 run 的 JSONL，最大 80MiB，以 Base64 经 RPC 返回 | 增加按问题选取范围、上次 run 索引和流式诊断包保存 |
| Windows `startup.log` 与 panic hook 位于 runtime trace 初始化之前 | 纳入诊断包；补齐各平台早期启动和异常退出的证据范围 |

2026-11-08 的生产日志任务已完成代码与自动验证，任务状态仍包含 Windows 实机验收项。2026-11-10 的生产成本回放已接近正常写入上限：约 318.6KiB/min，健康构造与编码 P95 约 0.167ms。新增字段和事件需要重新通过预算门。

### 固定边界

- Vue 3 + TypeScript 负责现有事实的展示与前端观测，Tauri + Rust 负责有效策略、文件预算、采集任务元数据和持久化导出。
- 扩展现有 `runtime_trace`、RPC 与分析器；沿用现有 writer、Browser StatsService 采样时钟和 geometric navigation。
- 模式与面板开关只影响诊断观测和工具能力。认证、信令、WebRTC、恢复、渲染策略及手柄路由保持同一业务合同。
- `main` 覆盖 Browser，`rust` 的 Native WIP 使用同一诊断外壳和能力声明。Browser 物理 scanout、ReferenceChain 等字段按真实 backend 标记能力。
- 发行渠道和诊断模式分别表达用途：stable / beta / Native WIP 是发行身份，development / production 是诊断策略。发行包统一使用生产策略。

## 方案比较

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 用户手动选择开发或生产 | 操作直接，切换灵活 | 发行端工具边界与性能预算容易混杂；有效值与用户选择需要额外解释 |
| 构建确定模式，生产仅在手动开始后采集 | 常态成本最小 | 故障首次发生前的状态与操作缺少证据，启动故障依赖再次复现 |
| 构建确定模式，生产基础记录常开并提供问题采集 | 偶发故障可回溯，主动复现有明确边界，产品入口简单 | 需要严格落实容量、采集成本、保存期限与数据投影 |

推荐第三项。现有生产 trace 已提供其核心记录能力，本轮重点是模式、入口和故障交付物的整理。

## 推荐方向

### 1. 两个模式的合同

| 项目 | 开发模式 development | 生产模式 production |
| --- | --- | --- |
| 生效条件 | 开发构建启动时自动生效 | stable、beta、Native WIP 等发行构建自动生效 |
| 首要目标 | 快速理解过程、检验假设、验证回归 | 回溯故障、整理复现条件、提供有效诊断证据 |
| 基础记录 | 包含生产核心证据，并按诊断维度增加详细事件 | 生命周期、错误、配置变化、操作结果及有界健康摘要 |
| 详细观测 | 模块级 trace、细粒度统计、策略原因、资源代次 | 自动异常与用户标记触发前后窗口，常规操作保留结果 |
| 调试工具 | 打开 DevTools、模块筛选、快照、日志目录入口 | 当前采集状态、主动采集、失败直接导出 |
| 高频或高成本探针 | 开发者主动启用，显示运行状态并限定期限 | 使用生产合同中的有界数值观测 |
| 文件轮转 | 沿用 64MiB × 10 | 沿用 16MiB × 5 |
| 数据处理 | 凭证、账号和内容经过安全投影 | 固定字段白名单和安全投影，导出时再次校验 |

开发模式中的 DevTools 和高成本探针按需启用，默认详细日志也执行限频与惰性构造。逐帧/逐包元数据、像素读回和现有测试注入工具设为明确的开发操作，并记录启停、期限与测量影响；针对性能复验，开发构建可通过启动参数选择已有 production 策略。开发记录提供与生产一致的核心摘要，再追加详细事件，便于同一分析器比较两种模式。

Rust 返回 `effectiveMode`、构建诊断能力、策略代次和预算。前端展示并消费该结果；前后端能力不一致时使用 production 并记录配置异常。开发期的策略选择作用于本次运行，用户配置继续保存画质、输入等产品选项。

旧 `debug` 和手动日志档位从产品设置移除。旧模式值在迁移时映射到构建默认值，包括历史 off；迁移记录一次策略变化并更新页面说明。生产模式内的“轻量后台采集”控制健康记录的保留密度，模式标签仍由构建确定。writer 的可用性单独展示为“正常、空间不足、写入失败”等诊断状态。

### 2. 常规与轻量后台采集

生产端默认选择“常规”，每 5 秒保留健康周期摘要；稳定运行后用户可选择“轻量”，每 30 秒保留一次。两档均自动保留异常窗口；两种有效模式继续为 development 和 production。

- 启动、退出、关键配置变更和最终操作结果保留结构化事件。请求失败与运行异常始终进入问题记录。
- 健康统计复用现有采样时钟与业务计数；稳态保留小型内存环形上下文，周期性落盘使用聚合检查点。建议稳态健康写盘收敛为约 30 秒一次，具体字节与覆盖合同由实施 RFC 验证。
- 请求失败、建连失败、持续卡顿、输入操作失败等事实触发有界详细窗口；恢复稳定后自动返回轻量记录。同一问题的重复失败合并，保留首次、末次、次数和代表性结果。
- 内存、磁盘、详细窗口和连续触发均有上限；文件按容量与保留期限轮转。页面关闭后停止诊断界面的刷新，采集器继续按策略运行。空闲且没有活动会话时沿生命周期事件记录。

用户选择“常规”后提高健康记录保留密度，便于较长时间观察健康变化。主动采集期间采用明确的采集合同；用户选择的后台档位在任务结束后恢复生效。

轻量策略涉及现有 1Hz 持久化证据的调整。实施时保留同一网络、恢复链、media supply、steady supply、submit/present 长尾和帧供给 delta 口径；验证环形上下文冻结、聚合覆盖、未知值与损失声明，以及分析器对两种保留密度的兼容性。新增诊断 getStats、DOM 读取和像素读回次数保持为 0。

### 3. 请求失败时直接导出

所有向用户呈现的请求失败位置沿用现有错误信息与恢复动作，旁边统一提供“导出日志”。登录、主机/游戏列表、连接、设置保存、更新等操作共用这个入口。

失败结果产生时就创建对应问题记录。记录关联本次操作的开始、阶段、结果、错误分类、状态码、耗时、重试次数、相关配置与环境，以及实际可用的前后上下文；请求字段沿安全投影保存。问题范围和类别由失败入口确定。

用户点击“导出日志”后直接调用系统保存对话框，文件名称自动生成，保存为一个诊断 ZIP。当前可用证据先形成一致的截止点，后续异常窗口继续补齐本地问题记录。正在运行的采集继续执行，导出包含截止点之前的可用记录。

保存成功提示“日志已保存”。用户取消保存后留在原页面，已有问题记录继续保留。保存失败展示错误与重试入口；实际覆盖不足时，提示与包内清单同时注明可用范围。

### 4. 用户主动采集

高级诊断的“开始采集”点击后立即生效，默认最长 10 分钟。状态显示“采集中 · 剩余 09:58”，按钮原位置变为“停止并导出”。用户照常复现登录、列表、连接、画面或输入问题；错误自动归入当前任务。

用户可以关闭诊断页、收起串流菜单或最小化应用，采集继续在后台运行，状态界面停止高频刷新。采集所需的详细证据仍按显式任务合同保留；稳定运行时的低成本后台记录由“轻量后台采集”选项管理。

“停止并导出”固定截止点后直接进入系统保存。到达期限则自动停止并形成可导出的本地记录，提示“采集完成，可导出日志”。页面关闭与采集停止分别由各自动作处理。

首版界面只提供自动关联的错误与主动采集范围。用户标记、问题类别填写、估计发生时间、范围筛选与下一次启动安排留作后续按实际诊断缺口扩展。导出的操作时间线用于辅助重建复现条件。

### 5. 后台自动记录问题

生产模式即使处于后台，也根据现有操作结果、异常 episode 和生命周期事实自动记录问题。建连失败、首帧失败、持续供帧异常、输入失败、关键 RPC 错误、恢复耗尽等保存详情；首版自动问题记录保留前 10 秒可用安全摘要 / 后 10 秒窗口。

每个问题同时记录：发生了什么、涉及哪个操作、何时发生、当前安全配置与环境、前后状态、已知错误与证据缺口。请求开始与阶段事实需要在失败发生前保留有界上下文，后续详细采集负责后续窗口。

突然退出使用上次 run 的检查点与末次有效记录，标为“结束记录不完整”。下次成功启动恢复相关证据，在高级诊断显示“上次运行有问题记录，可导出”；panic 和明确失败事实提供更具体的原因。

自动采集保存问题片段，用户通过失败入口或高级诊断统一导出。重复问题复用已有片段并记录次数；健康运行时按轻量预算保留摘要，详细采集在窗口收口后自动降回基础策略。

### 6. 精简后的页面和操作

生产端高级诊断从上到下展示：

1. 只读模式与一句记录状态：例如“生产模式 · 后台采集”或“采集中 · 剩余 09:58”。
2. 两个按钮：“开始采集”“导出日志”。主动采集中，前者原位置更新为“停止并导出”；后者导出当前可用记录。
3. 两个后台档位：“常规”（默认，低频采集）和“轻量”（稳定时进一步减少记录）。
4. 自动异常与主动采集的历史列表，显示时间、类别、状态、重复次数和逐条导出。

存在自动问题记录时，在状态下方显示“最近记录到连接失败 · 14:32”，点击“导出日志”优先选择最近问题。当前主动采集优先导出当前任务；其他情况使用本次运行的可用范围。范围、实际配置与日志覆盖由系统自动组织，导出直接进入系统文件对话框。

串流菜单沿用同一任务和按钮。失败页统一提供本次问题的“导出日志”，与当前错误直接关联。保存、采集和自动故障记录共用一套服务与容量管理。

鼠标、键盘、触屏与手柄执行相同操作。A / Enter 确认，B / Esc 关闭当前界面；关闭后焦点回到来源，串流输入沿既有持键释放门恢复。状态变化原位更新按钮，保持焦点和布局稳定。

开发端沿用同一采集与导出操作，默认详细记录生效；开发工具折叠展示 DevTools、模块筛选、快照和日志目录。

上一版原型已验证跨页面采集、标记、导出说明保留、模拟保存结果、启动安排、弹层键盘循环和窄窗口布局。本节是用户新要求下的简化设计，直接导出、轻量后台策略与精简页面进入下一阶段验证。实施验证包括请求失败关联、导出截止点、后台持续、自动降频、重复异常合并、跨 run 恢复、空间失败、采集期限和实际性能预算。

### 7. 统一诊断包

建议导出单个 ZIP 文件；现有 JSONL 作为包内可独立分析的证据文件。包内容按能力和有效范围生成：

| 文件 | 内容 |
| --- | --- |
| `manifest.json` | 包版本、模式、构建/commit、平台与运行能力、capture/run/session、时间范围、文件 hash、缺失与 flush 状态 |
| `runtime-trace-*.jsonl` | 本问题范围内的有序记录；保留现有 schema v3 和生产合同字段 |
| `config-snapshot.json` | 请求配置与实际生效配置、输入与显示相关安全值、阶段变化 |
| `system-summary.json` | OS/WebView/架构、renderer/decoder 能力、窗口/显示与网络路径类别 |
| `startup-summary.json` | 早期初始化、启动失败与异常退出的安全摘要，注明原始证据的可用性 |
| `reproduction.json` | 自动关联的问题类别、失败时间、静态操作序列与实际结果 |
| `summary.md` | 故障时间线、主要异常、配置变化、操作结果、六段指标及证据覆盖 |

`summary.md` 基于同一分析模型生成，结论具有数据来源、样本数与覆盖范围。生成与导出使用后台任务；流式文件保存控制大包的内存与 IPC 开销。

地址、账号、设备、游戏和动态 UI 使用类别或包内安全引用。自动采集的 token、cookie、授权原文、完整 URL/SDP 和用户输入内容经过白名单投影。游戏/设备引用由用户在测试环境中对应目标。原始启动文本和 panic message 同样经过安全投影；用户自行补充复现说明、截图和视频。

本地采集与本地导出为默认交付路径，分享由用户操作完成。

### 8. 容量、保留与成本

以下是建议的首版验收参数；新增采集操作在已有速率预算内运行。

| 项目 | 建议值 |
| --- | --- |
| 生产滚动 trace | 16MiB × 5，共 80MiB；最长保留 7 天，容量上限先触发则先轮转 |
| 开发滚动 trace | 64MiB × 10，共 640MiB；最长保留 7 天 |
| 主动采集 | 默认 10 分钟，回溯实际可用的有界上下文 |
| 单份生产诊断包 | 内容未压缩字节总量 ≤32MiB，超出则缩小时间范围并明确标记 |
| 应用内保存的生产包 | 最近 2 份，总量 ≤64MiB，最长保留 7 天 |
| 应用管理的生产诊断总空间 | ≤160MiB，包含 trace、保存包、早期日志、索引和临时文件；写入前预留空间 |
| 常规串流写入 | ≤320KiB/min；持续输入单独 ≤64KiB/min |
| 异常详细记录 | 额外 ≤128KiB/min；前 5s / 后 10s、约 4Hz，复用冷却与合并 |
| 健康摘要构造与编码 | P95 ≤0.5ms/次；新增诊断 getStats/DOM/像素读回次数为 0 |

活动任务的必要范围在同一总容量内保留；空间不足时缩短可保存范围，并记录覆盖缺口。归档与临时文件共用预算，后台任务在正常退出、取消和失败时收口。用户自行导出到应用目录之外的文件由用户管理。

开发包按选定范围导出，保留现有 80MiB 内容上限；详细日志完整目录仍遵循开发预算。两种模式都把队列压力、丢弃、IPC 超时、writer IO 与写盘截止点记入包内清单。

### 9. 分析与复现闭环

分析器复用 `analyze-runtime-logs` 和生产健康报告，先验证文件身份、顺序、时间窗、采样与结尾覆盖，再生成结论。

串流结论同时覆盖网络健康、恢复链健康、media supply、steady supply、submit/present 长尾与帧供给 delta。Browser 的视频推进、WebGL 提交、GPU 完成上下界和物理上屏分别保持真实语义；能力缺失使用 UNSUPPORTED，证据覆盖不足使用 INSUFFICIENT_EVIDENCE。

复现按三个步骤进行：从包中恢复对应构建与安全配置；按操作序列重建平台、输入、显示与网络条件；将可确定的异常事件和操作结果转成回归 fixture。账号授权、远端主机和服务内容由测试环境提供。包内操作时间线用于辅助复现，自动执行以现有测试入口和明确脚本为依据。

## 待验证事项

- 10 分钟主动采集、有界上下文、7 天保留、两份保存包为建议初值，结合实机故障周期调整。
- Windows、macOS、Linux 的启动/崩溃日志可用性需要分别审计；Windows 当前文件出口已确认，macOS/Linux 的早期出口需要补齐设计。
- 生产日志当前已接近稳态字节预算；优先通过导出侧元数据和现有摘要组织信息，新增运行事件经回放复算。
- DevTools 的构建 capability、失败问题关联、轻量后台策略、上次 run 保留索引及 ZIP 流式保存需在实施 RFC 中固定具体接口。
- 后续增强的领域由真实诊断包缺口决定；首版优先完整交付双模式、生产取证和导出闭环。

## 候选后续任务

1. **双模式与高级诊断收敛（complex）**：统一有效模式、构建能力和旧配置迁移；调整页面和开发工具入口。验证开发/发行及前后端能力不一致场景。
2. **生产问题采集与诊断包（complex）**：复用现有 trace 实现请求失败直接导出、主动采集、异常自动取证、稳定降频与有界保存；补齐包内容、跨 run 索引、流式导出和分析消费。
3. **操作指引与验收记录（simple，依赖前两项）**：形成用户取证说明和开发复现流程；覆盖登录失败、建连失败、持续卡顿、菜单失效、设置失败与异常退出。

前两项进入同一实施 RFC，分阶段验证。开发/生产对照验证媒体与输入执行序列，专项验证预算、隐私投影、轮转、跨 run、磁盘失败和取消收口。实机启动、串流及长测由用户手动验收；每个故障场景最终以“一份包能重建问题时间线和复现条件”为交付标准。
